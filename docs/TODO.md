## 一、已知缺陷（未解决）

### 1.1 实时监控推流间歇性降速　⚠️ 优先级最高

**现象**：`--smoke-live` 连续跑 5 次约有 2 次失败，客户端接收帧率从正常的
24.6~25.0 FPS 塌到 0~5 FPS。有时表现为"HTTP 200 但零字节"。

**已经排除的**：

| 怀疑对象 | 结论 |
| --- | --- |
| 服务端管线性能 | ❌ 隔离测量稳定 30.0 FPS，反复验证 |
| 客户端解码/绘制瓶颈 | ❌ 只解码每批最后一帧后无改善；成功时能跑满 25 FPS |
| 服务端异常 | ❌ `data/server.log` 无任何 WARNING/ERROR/traceback |
| 设备枚举阻塞 | ❌ 已加失败缓存，问题依旧 |
| 推流线程忙等待 | ❌ 已改条件变量，问题依旧 |

**关键矛盾**：失败时服务端日志显示"已发送 400+ 帧"，而客户端只收到几十帧。
两端对同一段传输的计数严重不一致 —— 问题出在 TCP 传输/接收路径，
不在两端的业务逻辑。

**已做的缓解**：客户端推流看门狗（连上后 2.5 秒无数据自动重连，最多 3 次）。
但它治标不治本 —— 失败模式不是"零字节"而是"极慢"。

**下一步**：在客户端记录每次 `readyRead` 的时间戳与字节数，
与服务端每次 `wfile.write` 的时间戳对齐，定位数据滞留在哪一段。
服务端日志已经落盘到 `data/server.log` 就是为这个准备的。

### 1.2 `/cameras` 设备枚举偶发失败

曾观察到 `GET /cameras` 返回 500（根因是设备枚举抛异常）。
已做防御性处理：每个设备序号独立兜底、枚举失败也写缓存（短 TTL）、
端点整体不再因枚举失败而返回错误。

**未做**：根因未定位（可能是某台设备被其它进程占用时的驱动行为）。
当前表现是"偶发少列出一个摄像头"，不影响推流。

### 1.3 实时监控页的「摄像头」下拉框可能为空

截图里观察到下拉框无内容。可能是枚举那次恰好失败，也可能是渲染问题。
未复现确认。若稳定复现，检查 `LiveView::onCamerasReceived` 里
`m_deviceCombo->addItem` 的分支与 `m_devices_cache` 的时序。

## 二、阶段 3：告警规则与联动（让项目闭环）

**这是当前最有价值的后续方向**：现在的系统检测出违规只是写进数据库，
现场没人知道。补上这条链路，项目才从"图像查看器"变成"有闭环的系统"。

### 2.1 规则引擎（服务端，可配置）

- **连续 N 帧命中**才触发 —— 抑制单帧误报，这是告警系统的基本功
- **时间窗内累计 M 次** —— 抓"反复违规"而不是"偶然一次"
- **类别过滤** —— 只看未佩戴，或也看佩戴不规范
- **ROI 区域** —— 只在画面指定区域内判定（例如只关心工位，不关心走道）
- **冷却时间** —— 同一事件不重复轰炸

### 2.2 输出通道（可多选）

- 界面告警横幅 + 声音
- 审计表（独立于检测记录，按"事件"而不是"图片"组织）
- 抓拍留证（触发时存一张带时间戳的原图）
- HTTP webhook（对接 MES / 钉钉 / 企业微信）

> **注意**：若抓拍由实时管线产生，**要保存未镜像的原始帧** ——
> 镜像是显示变换，不该进入证据链。

### 2.3 客户端「告警记录」页

按事件组织，支持按时间/类型/摄像头筛选，可查看触发时的抓拍。

## 四、质量与工程

### 4.1 检测精度评测　⚠️ 落地前必须做

**当前没有任何测试集指标**（mAP、精确率、召回率、误报率）。

工业现场**误报比漏报更致命** —— 工人被误报警三次就不信这个系统了。
要真正落地必须先做评估：

- 标注一批测试集（不同光照、角度、遮挡程度）
- 算各类别的 P/R/F1 与混淆矩阵
- 特别关注「佩戴不规范」这一类（最容易误判）

### 4.2 端到端自动化

当前所有验证都是手动脚本（`--selftest` / `--smoke-*` / `tests/run_tests.bat`），
已经具备无人值守能力，但还没有串成流水线。

可以用 GitHub Actions 做：构建 → 单元测试 → 离线冒烟（不含摄像头）。
**注意**：仓库是私有的，且推理需要 GPU —— CI 里只能跑不依赖模型的那部分
（`--check-i18n`、`--dump-layout`、单元测试）。

### 4.3 单元测试覆盖面

目前只有 `SseParser` 与 `MjpegParser` 有单测（31 项）。
这两个是"边界密集、手工难复现"的模块，覆盖它们是正确选择。

可补的：`Protocol`（JSON 解析容错）、`HistoryProxy`（筛选逻辑）、
`BatchController`（背压调度）。

## 六、明确不做（以及为什么）

**人脸识别 / 身份追溯**

要回答"是谁没戴"就必须上人脸识别，而人脸是敏感个人信息，
涉及《个人信息保护法》的单独同意、最小必要、存储期限等义务。
为了省一个班组长的巡检而背这个法律包袱，不值得。

**Web UI**

服务端刻意保持"薄"——只做推理与数据，不做界面。
这是"HMI 与视觉管线分离"的分工。浏览器预览工具（`server/tools/preview.py`）
只是验证手段，不是产品形态。

**自建训练流程**

模型来自早先的协作项目。本项目定位是"让训练好的模型在工业现场跑得稳"，
不涉及训练。换模型只需把 `.pt` 放进 `yoloserver/models/checkpoints/`。
