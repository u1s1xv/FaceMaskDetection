# 后续计划：摄像头接入与实时检测

> 本文档基于**本机实测数据**制订，不是估算。测量脚本与方法见文末。

## 一、目标

把当前"单图 / 批量文件夹"的离线检测，扩展为**摄像头实时检测 + 告警联动**：

```
当前：  图片 ──► 推理 ──► 存库 ──► 人工去看历史记录
目标：  摄像头 ──► 推理 ──► 实时画面叠加 ──► 规则判定 ──► 告警动作 ──► 留痕
                                              ↑
                                        这一步才是"联动"
```

"检测到"和"有人管"之间隔着一条鸿沟 —— 现在的系统检测出违规只是写进数据库，现场没人知道。补齐这条链路，项目才从"图像查看器"变成"有闭环的系统"。

## 二、实测数据（决定了架构，请先看这个）

测试环境：RTX 3060 Laptop / YOLOv12n / 本机 640×480 摄像头。

| 测量项 | 结果 | 对架构的影响 |
|---|---|---|
| 推理 @imgsz=320 | 21.1 ms | **降 imgsz 不提速** |
| 推理 @imgsz=640 | 20.9 ms | 所以直接用 640，精度白拿 |
| 推理 @imgsz=416 | 23.0 ms | 瓶颈在 ultralytics 框架开销（预处理/NMS/结果构造），不在 GPU 算力 |
| 采集 DSHOW | 15.0 FPS | **DSHOW 只有 MSMF 的一半** |
| 采集 MSMF | **31.3 FPS** | 默认用 MSMF |
| 采集 ANY | 29.5 FPS | 自动选择即可 |
| cv2 画框（5 个框） | 0.12 ms | 几乎免费 |
| JPEG 编码 640×480 | 0.57 ms / 25.6 KB | 20fps 只需 0.5 MB/s |
| 推理（annotated=False） | 19.63 ms | |
| **实时快路径合计** | **20.32 ms → 49.2 FPS** | 单路可跑满采集帧率 |
| 现有标注路径 | 69.69 ms → 14.4 FPS | **标注一项吃掉 50 ms** |

**两条关键结论**：

1. **瓶颈在采集（31 FPS），不在推理（49 FPS）**。单路摄像头可以跑满帧率，不需要跳帧推理。
2. **现有标注路径慢 3.4 倍**，因为走的是 PNG 编码。实时视频必须走独立的 JPEG 快路径，**不能复用** `_create_beautified_image`。

## 三、四个关键设计决策

### 决策 1：采集放在服务端（Python + OpenCV），不在客户端

| 方案 | 评估 |
|---|---|
| **服务端 cv2.VideoCapture** | ✅ 推荐。USB / RTSP / 视频文件统一接口；采集与推理同进程，帧不跨进程 |
| 客户端 Qt5 Multimedia | ❌ Qt5 的 Windows 后端基于 DirectShow，多年不维护，RTSP 支持差 |
| 客户端采集后传帧给服务端 | ❌ 640×480 RGB 每帧 900 KB，20fps 就是 18 MB/s，纯浪费 |

服务端是"视觉管线"，客户端是"HMI" —— 保持这个分工。

⚠️ **注意**：这个方案假设摄像头接在运行服务端的机器上。对于本项目的单机上位机形态成立；若将来要"客户端 A 看远程机器 B 的摄像头"，需要另加一层流转发（不在本计划范围内）。

### 决策 2：实时视频用**服务端标注 + MJPEG**，与单图/批量的"客户端自绘"相反

这看似自相矛盾，其实是**约束不同**：

| 场景 | 主要约束 | 选择 | 实测依据 |
|---|---|---|---|
| 单图 / 批量 | **带宽** | 客户端自绘 | 服务端 PNG 1565 KB vs 客户端 JSON 2 KB，快 2.9 倍 |
| 实时视频 | **时序一致性** | 服务端标注 | 框与帧分两个通道传，任何抖动都表现为"框在画面外飘" |

实时视频如果分两路传（MJPEG 画面 + SSE 检测结果），需要自己做帧序号对齐，且网络抖动时会看到框滞后于画面。而服务端标注的成本实测只有 **0.69 ms/帧**（画框 0.12 + JPEG 0.57），代价几乎为零。

> **面试价值**：同一个系统里两条渲染路径，能讲清"为什么这里反过来选"比只会背一个方案更有说服力。

### 决策 3：不用 ultralytics 的 `stream=True`，自己控制帧循环

必须实现 **latest-frame-wins**（只取最新帧，丢弃积压的旧帧）。如果排队处理，推理速度低于采集速度时延迟会持续累积，画面越来越滞后。丢帧只会掉帧率，不会累积延迟 —— 实时系统宁可掉帧也不要延迟。

### 决策 4：不做人脸识别

"是谁没戴"需要人脸识别，而人脸是敏感个人信息（《个人信息保护法》要求单独同意、最小必要、存储期限限制）。性价比极低。

**改为"不认人，只报警"**：工位防护不到位就声光提示现场整改 + 留一张带时间戳的抓拍。既有效，又避开法律风险。

### 阶段 1：视频源抽象与采集 ✅ 已完成

**产物**：[`server/camera.py`](../server/camera.py)（`CameraSource` / `FrameSlot` / `CameraManager`）
· [`server/tools/make_test_video.py`](../server/tools/make_test_video.py)（合成虚拟摄像头源）
· [`server/tools/test_camera.py`](../server/tools/test_camera.py)（17 项验证）

**接口**：`GET /cameras` · `POST /cameras/open` · `POST /cameras/{id}/close` · `GET /cameras/{id}/stats`

**实测**：虚拟摄像头 30.0 FPS，真实 USB 摄像头 30.4 FPS（MSMF），两路并行互不干扰。

#### 实现中踩到的五个坑（都已修，写在这里免得重犯）

**1. 采集后端必须按源类型区分。** 最初对所有源统一试 MSMF → DSHOW → ANY，
结果用 MSMF 打开一个 29 秒的 mp4，**读首帧花了 76 秒**。
MSMF/DSHOW 是摄像头专用后端，文件与网络流必须交给 FFMPEG。改完首帧 6 ms。

**2. 文件源必须按源帧率节流。** 解码器会全速跑 —— 实测 3 秒把 29 秒的片子放完了（286 FPS），
虚拟摄像头完全失真。现在读 `CAP_PROP_FPS` 并按 1/fps 放帧，稳定在 30.0 FPS。

**3. FrameSlot 必须区分"是否有新帧"。** 最初 `get()` 无条件返回最新帧，
结果推理侧轮询速度远高于采集，**同一帧被"消费"了 22 次**（实测 151 帧被消费 3356 次）。
现在没有新帧就返回 None，不重复处理。

**4. 统计量需要独立的锁。** 采集线程无锁写 `_fps_window`、`fps` 属性加锁读，保护不一致，
算出了 489 FPS 这种不可能的值。现在统一用 `_stats_lock`，且样本不足 5 个时
退回"总帧数 / 运行时长"，避免启动瞬间出现假数字。

**5. 枚举设备有开销，必须缓存。** 逐个序号试打开设备一次要好几秒，
界面上刷新设备列表不能等这么久，加了 30 秒 TTL 缓存。

> **一句话总结**：实时视频的坑几乎都不在"能不能跑"，而在**语义边界**——
> 什么算新帧、什么时候该丢、什么源配什么后端。这些用肉眼看不出来，必须写成断言。

- `server/camera.py`
  - `CameraSource` 类：封装 `cv2.VideoCapture`，默认 MSMF，可配置后端
  - **独立采集线程** + 单帧环形缓冲（latest-frame-wins）
  - 断流检测与自动重连（USB 摄像头拔插、RTSP 抖动）
  - 统计：采集帧率、丢帧数、重连次数
- REST 接口
  - `GET /cameras` —— 枚举本机可用设备
  - `POST /cameras/{id}/open` / `close`
- **验证**：连开 10 分钟不断流，帧率稳定在 30 FPS 附近

### 阶段 2：实时推理与推流（核心）⚠️ 已可用，但存在一个未定位的间歇性故障

**已完成**：
- 服务端 [`server/live.py`](../server/live.py) + `GET /cameras/{id}/stream.mjpg`（MJPEG）
- 服务端 [`server/tools/preview.py`](../server/tools/preview.py)（浏览器预览，用于快速验证）
- 客户端 `MjpegParser`（增量解析，20 项单元测试）+ `VideoWidget` + `LiveView`「实时监控」页
- 客户端 `--smoke-live <源> [秒]` 自动化验证入口

**正常情况下的实测**（真实 USB 摄像头 / 视频源 640×480）：

| 指标 | 数值 |
| --- | --- |
| 服务端采集 | 30.0 FPS |
| 服务端推理 | 19~22 ms |
| 服务端端到端延迟 | 31~51 ms |
| 服务端管线吞吐 | 30.0 FPS（隔离测量） |
| **客户端接收** | **24.6 ~ 25.0 FPS**（即服务端 25fps 推流上限） |
| MJPEG 帧完整性 | 393/393、403/403 完整 JPEG |

---

#### ⚠️ 未解决：间歇性推流降速（约 1/3 概率）

**现象**：`--smoke-live` 连续 5 次约有 2 次失败，表现为客户端接收帧率塌到
0 ~ 5 FPS（成功时是 24.6~25.0 FPS）。有时是"HTTP 200 但零字节"。

**已经排除的**：
- ❌ 服务端管线性能 —— 隔离测量稳定 30.0 FPS，反复验证
- ❌ 客户端解码/绘制瓶颈 —— 只解码每批最后一帧后无改善；且成功时能跑满 25 FPS
- ❌ 服务端异常 —— `data/server.log` 里没有任何 WARNING/ERROR/traceback
- ❌ 设备枚举阻塞 —— 已加失败缓存，问题依旧
- ❌ 推流线程忙等待 —— 已改条件变量，问题依旧

**关键矛盾**：失败的那几次，服务端日志显示"已发送 400+ 帧"，而客户端只收到几十帧。
两端对同一段传输的计数严重不一致 —— 说明问题出在 TCP 传输/接收路径，
而不是两端的业务逻辑。

**已经做出的缓解**（治标，但值得保留）：
- 推流看门狗：连上后 2.5 秒无数据自动重连（最多 3 次）
- 服务端文件日志 `data/server.log` —— 客户端把服务端当子进程，
  其 stderr 被管道接走，客户端一挂就丢失，必须落盘

**下一步建议**：在客户端记录每次 `readyRead` 的时间戳与字节数，
和服务端每次 `write` 的时间戳对齐，定位数据是在哪一段滞留的。

**已完成**：[`server/live.py`](../server/live.py)（`LivePipeline`）+
`GET /cameras/{id}/stream.mjpg`（MJPEG）+ [`server/tools/preview.py`](../server/tools/preview.py)（浏览器预览）

**实测**（真实 USB 摄像头，640×480）：采集 30.0 FPS · 推理 ~20 ms · 端到端 ~50 ms
· JPEG 28 KB/帧 · 推流 23 FPS（受 25fps 限速）

**已完成**：Qt 客户端「实时监控」页（`MjpegParser` 增量解析 + `VideoWidget`）

#### 画面镜像（一个容易忽略的显示决策）

摄像头原始输出是不镜像的。桌面应用的惯例是**镜像显示**（像照镜子，视频会议的
本地预览也如此），而工业监控的惯例**不镜像**（画面左右与现场一致，
指挥"往左一点"才不会说反）。两者都有道理，所以做成了开关，默认镜像。

实现上有个坑：**服务端把帧率/延迟这些 OSD 文字画在画面里**，
如果在客户端整体翻转，文字会变成镜像的、没法读。所以必须在服务端翻，
且要在画 OSD 之前。

另一个选择：翻转的是**检测框的 x 坐标**，而不是"先把画面翻过来再推理"。
这样推理永远跑在原始像素上，检测结果与镜像开关无关 ——
关掉镜像不会得到另一组结果。已验证坐标变换精确（640-365.2=274.8）。

#### 实现中踩到的三个坑

**1. 推流发送循环的判断顺序写反了。** 初版写成：

```python
if seq != last_seq:
    last_seq = seq          # 先赋值
if seq == last_seq and ...  # 再和自己比 —— 恒为真
```

结果每轮都 `continue`，**一帧都发不出去**。而且表面上连接是成功的
（HTTP 200、Content-Type 正确），极具迷惑性。正确写法是先用旧值比较、再更新。

**2. 日志刷屏。** `run_inference` 每次写一行日志，实时路径 30fps 就是 30 行/秒。
加了 `quiet` 参数。

**3. 缺 `import time`。** 推流函数在 `try` 之前用了 `time.time()`，异常直接冒到外层，
表现为"连接建立后立刻 500"。教训：`py_compile` 抓不到这类问题，
应该把整个 server 目录的模块都 import 一遍做静态检查。

- 推理线程：取最新帧 → 推理（`annotated=False`）→ cv2 画框（含中文类别名映射）→ JPEG 编码
- **MJPEG 端点** `GET /cameras/{id}/stream.mjpg`（`multipart/x-mixed-replace`）
- 客户端新增「**实时监控**」页
  - `QNetworkAccessManager` 增量解析 MJPEG 流（与已有的 `SseParser` 同思路，可复用边界处理经验）
  - 画面区域、开始/停止、摄像头选择、分辨率选择
  - OSD 叠加：实时帧率、目标数、时间戳
  - 侧栏实时统计：当前画面各类别计数、最近一次违规
- **验证**：端到端延迟 < 150 ms；稳定 ≥ 25 FPS；连续运行 30 分钟无内存增长

### 阶段 3：告警规则与联动（让项目"闭环"）

## 五、风险与未知

| 风险 | 影响 | 应对 |
|---|---|---|
| **MSMF 兼容性** | 部分 USB 摄像头在 MSMF 下打不开，而 DSHOW 只有一半帧率 | 后端可配置 + 自动降级 + 在界面上暴露实际帧率，让用户看得见 |
| **误报率未知** | 告警功能上线后误报会成为主要投诉 | 先做规则层抑制（连续 N 帧）；后续需要标注测试集评估 mAP/误报率 |
| **长时间稳定性** | 摄像头断流、内存增长、句柄泄漏 | 阶段 1 就做重连；阶段 4 专门压测 |
| **无摄像头环境** | 无法开发/演示 | 支持**视频文件作为虚拟摄像头源**，可复现、可回归测试 |
| **RTSP 支持** | 网络摄像头延迟/花屏 | cv2 支持，但需实测；暂不作为验收项 |

## 七、附：测量方法

所有数据由以下脚本产出，可复现：

- 摄像头枚举与后端对比：`cv2.VideoCapture(idx, backend)` 循环计数
- 推理帧率：`detector.get_detector().run_inference(image_data=frame, annotated=False)` 循环 20 次取平均
- 快路径：推理 + `cv2.rectangle`/`putText` + `cv2.imencode(".jpg", q=80)`
- 关键前提：`image_data` 接受 **numpy 数组**，不是裸字节（app.py 中先 `cv2.imdecode`）
